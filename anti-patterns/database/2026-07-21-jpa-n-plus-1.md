# [WEEK 2] - The N+1 Query Problem (JPA/Hibernate)

> **Category:** database
> **Severity:** 🟠 High

---

## ❌ The Anti-Pattern

A developer maps a parent-child relationship with `@OneToMany(fetch = FetchType.EAGER)` — or leaves the default lazy loading in place and then loops through parent entities calling `parent.getChildren()` — assuming JPA will "just handle it efficiently." It does not. Hibernate first fires **1 query** to load the parents, then fires **N additional queries** — one per parent — to hydrate each child collection. Load 500 orders and you don't run 1 query; you run **501**. The code looks clean, the ORM hides the SQL, and nobody notices until the endpoint hits production data volumes.

---

## 🧨 The Flawed Code

```java
@Entity
@Table(name = "orders")
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String customerName;

    // EAGER on a collection: every Order load drags line items along,
    // one extra SELECT per Order row.
    @OneToMany(mappedBy = "order", fetch = FetchType.EAGER)
    private List<LineItem> lineItems = new ArrayList<>();

    // getters/setters omitted
}
```

```java
@Service
public class OrderService {

    private final OrderRepository orderRepository;

    public OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }

    // Looks innocent. Returns 500 orders for the admin dashboard...
    public List<Order> getRecentOrders() {
        return orderRepository.findTop500ByOrderByCreatedAtDesc();
    }
}
```

```java
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @GetMapping("/recent")
    public List<Order> recentOrders() {
        // During JSON serialization, every order's lineItems collection
        // is touched — and with lazy loading, EACH touch is a new SELECT.
        return orderService.getRecentOrders();
    }
}
```

Turn on SQL logging and watch the explosion:

```properties
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
```

```
-- 1 query for the parents:
SELECT o.id, o.customer_name, o.created_at FROM orders o ORDER BY o.created_at DESC LIMIT 500;

-- ...then 500 nearly identical queries, one per parent:
SELECT l.id, l.order_id, l.sku, l.quantity, l.price FROM line_items l WHERE l.order_id = 1001;
SELECT l.id, l.order_id, l.sku, l.quantity, l.price FROM line_items l WHERE l.order_id = 1002;
SELECT l.id, l.order_id, l.sku, l.quantity, l.price FROM line_items l WHERE l.order_id = 1003;
-- ... 497 more of these
```

501 round trips. One HTTP request.

---

## 📉 The Theoretical Fallout

- **Performance:** Each round trip costs network latency (typically 0.5–2 ms inside a data center, far worse across zones). 500 extra queries × 1 ms = **half a second of pure latency** added to a single API call — before any actual work happens. Response time scales linearly with row count, so the endpoint gets slower every month as data grows.
- **Maintainability:** The bottleneck is invisible in the code. Profilers blame "the database," teams respond by adding indexes that don't help, and the real fix (fetch strategy) is hidden inside ORM annotations nobody reviews. `FetchType.EAGER` also *leaks*: every other query that touches `Order` — reports, schedulers, unrelated endpoints — now drags line items along whether it needs them or not.
- **Correctness:** Under load, the query storm exhausts the connection pool (see [The Ghost Connection Pool](../../war-stories/concurrency/2026-07-20-the-ghost-connection-pool.md)). Requests that never touch `line_items` start timing out too, and a "slow endpoint" becomes a cascading outage.

## ✅ The Refactored Code

**Option 1 — `@EntityGraph` (declarative, no JPQL needed):**

```java
public interface OrderRepository extends JpaRepository<Order, Long> {

    // Fetches orders AND their line items in a single JOIN query.
    @EntityGraph(attributePaths = {"lineItems"})
    List<Order> findTop500ByOrderByCreatedAtDesc();
}
```

**Option 2 — `JOIN FETCH` (explicit JPQL, full control):**

```java
public interface OrderRepository extends JpaRepository<Order, Long> {

    @Query("""
        SELECT DISTINCT o
        FROM Order o
        LEFT JOIN FETCH o.lineItems
        ORDER BY o.createdAt DESC
        LIMIT 500
        """)
    List<Order> findRecentWithLineItems();
}
```

**And remove the foot-gun from the entity** — collections should be lazy by default; the *query* decides what to fetch:

```java
@Entity
@Table(name = "orders")
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String customerName;

    // LAZY (the default for @OneToMany) — never fetch what wasn't asked for.
    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    private List<LineItem> lineItems = new ArrayList<>();
}
```

The SQL output, before and after:

```
-- AFTER: exactly 1 query. Parents and children in one JOIN.
SELECT o.id, o.customer_name, o.created_at,
       l.id AS li_id, l.sku, l.quantity, l.price
FROM orders o
LEFT JOIN line_items l ON l.order_id = o.id
ORDER BY o.created_at DESC
LIMIT 500;
```

501 queries → **1 query**. Response time: 850 ms → 45 ms.

---

## 🧠 The Core Principle

**"One query to rule them all": fetch exactly the data the use case needs, in as few round trips as possible.** JPA gives you three levers, and knowing when to pull each is the whole game:

- **Lazy loading** (default for collections): fetch only when accessed — correct default, but dangerous when access happens in a loop or during serialization.
- **Eager fetching / join fetching**: pull the graph in one query — correct when you *know* the use case needs the children, disastrous as a blanket entity-level default.
- **Batch fetching** (`@BatchSize(size = 50)` or `hibernate.default_batch_fetch_size`): the middle path — instead of 500 queries, Hibernate fetches children for 50 parents per query (500 → 11 queries). Useful when a JOIN would explode the result set (multiple collections = Cartesian product).

The deeper principle: **an ORM does not eliminate database thinking — it defers it.** Every abstraction that hides I/O will eventually punish you for forgetting the I/O exists.

---

## 🔍 How to Spot This in a PR

- `fetch = FetchType.EAGER` on **any** collection mapping (`@OneToMany`, `@ManyToMany`). There is almost never a good reason. Reject on sight.
- `getChildren()` / `getLineItems()` / any collection getter called **inside a loop or stream** over parent entities.
- A controller returning JPA entities whose JSON touches lazy collections outside a transaction — each serialization-triggered access is a hidden query.
- Integration tests or staging logs showing 10+ near-identical `SELECT ... WHERE parent_id = ?` statements for a single request. One duplicated query shape = N+1 in the wild.
- No `@EntityGraph`, `JOIN FETCH`, or DTO projection on repository methods backing list endpoints that render child data.
